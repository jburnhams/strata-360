### Learned so far
1. **OSV structure:** one MP4 with two HEVC Main10 video streams (3840×3840 each, one per lens), one AAC stereo audio, two `djmd` protobuf tracks, two `dbgi` debug tracks, an attached JPEG thumbnail.
2. **Frame timing is irregular:** nominal 50 fps but 239 frames in 4.82 s (spacing 20 ms, some 60 ms gaps, i.e. dropped frames). ffprobe's 49.59 fps is just the average. Timestamps must be read per frame.
3. **Timestamps:** filename and container `CreateDate` agree (2026-02-21 12:00:07). File mtime 14:00:13+02:00 = 12:00:13 UTC, so `CreateDate` is very likely **UTC**. Checked on one file only.
4. **Telemetry (`djmd`, protobuf `dvtm_oq101.proto`)**: 50 Hz packets. Track 1 carries per-frame exposure (ISO, shutter, colour temp), a unit quaternion orientation, more quaternion samples per packet (higher-rate attitude), and a 3-vector (probably accel). Track 2 carries the other lens's exposure and device identity. **No GPS** found (scanned for lat/long-like doubles and location strings; the camera has no built-in GPS).
5. **Each lens frame is a full circular fisheye** filling nearly the whole 3840×3840 frame (small dark corners). Lens 0 looks up-and-forward, lens 1 looks down-and-back in the sample (the camera is on a selfie stick held by the user, tilted).
6. **The user is clearly visible** in lens 0 (blue jacket, hydration vest), very close, with their hand and thumb across the lens edge. Other people are visible in both lenses. This confirms the selfie-stick prior in the README. Also seen: hand/thumb over the lens (obstruction) in both lenses, and water droplets on the lens in lens 0.

### Prior art (search results, 2026-09-30)
- **[OpenOSV](https://github.com/Kemerd/OpenOSV)** (Apache-2.0, C++20, about 87k lines). Reads the embedded calibration and IMU, stitches dual-fisheye with optical flow, seam carving and multi-band blending, does gyro stabilisation, and has an automatic **D-Log M → Rec.709/PQ/HLG colour pipeline** ("autohdr"). macOS Apple Silicon is supported with a **Metal** backend (community-tested on an M4). CLI `osvtool`: `probe`, `render --mode equirect|reframe`, `--color 709|pq|hlg|dlogm`, `--hdr-peak`, `--range`, `--frame`, `--device metal|cpu|opencl`. **Limitation: the CLI has no animated (keyframed) reframes**, so we would use it for the *stitch/colour/stabilise* stage and do our own keyframed reframing from its equirect output. No Python bindings; use it as a subprocess. Docs: `docs/FORMAT.md`, `docs/GEOMETRY.md`.
- **[OSV Toolbox](https://github.com/ChelouteVR/osvtoolbox)** (MIT): extracts/recomposes the OSV tracks; no stitching or calibration.
- **Gyroflow** has a built-in DJI profile, and needs no sync for DJI gyro data (relevant to stabilisation, not stitching).
- The ffmpeg `v360` route is the common generic approach (`ih_fov=190`), but nothing open source besides OpenOSV uses DJI's own calibration.

### The calibration (decoded from our sample)
Where: first `djmd` packet, `StreamMeta.6` = `PanoDewarpParams`, **24 slots**, 264 bytes each. Slots 1/2 = `native_refine` (slave/master), 11/12 = `native`, others = lens guard, underwater and far-field presets (per OpenOSV docs).

Per slot (values from our clip, slot 2 = master/front, slot 1 = slave/rear): `fx≈1049, fy≈1049, cx≈1909, cy≈1912` (slot 2) and `fx≈1047, fy≈1047, cx≈1910, cy≈1919` (slot 1) on the 3840 px frame; `k1..k4 = 0.0619, −0.0064, 0.0048, −0.0046` and `k5 = 0.00067` (slot 2); `0.0651, −0.0086, 0.0069, −0.0055` and `0.0008` (slot 1); extrinsic quaternion (w,x,y,z) about `(0.705, 0.709, −0.006, −0.010)` (slot 2) and `(−0.004, 0.006, −0.705, 0.709)` (slot 1); Euler angles in degrees also stored. Model is 5-term Kannala–Brandt: `theta_d = theta·(1 + k1θ² + k2θ⁴ + k3θ⁶ + k4θ⁸ + k5θ¹⁰)`, `u = cx + fx·theta_d·cosφ`. Image circle reaches about 1900 px radius at about 98° per lens (usable FOV about 195°, matching OpenOSV). So the image circle **fills the whole 3840×3840 frame**.

Other header fields decoded: `StreamMeta.4` (colour mode) is empty in our clip, which means **Normal** (D-Log M would be 19, HLG 9). IMU fields: `DeviceMultiAttitude` in `FrameMeta.3`, batches of 16–17 fused quaternions with a timestamp (microseconds since power-up), vsync and offset; IMU rate 1000 Hz.

- **Colour decision (user):** final output is **SDR (Rec.709)**. See README §8.9. HDR/log matters only during processing: the sample is Normal mode, but if footage is shot in D-Log M (or HLG) then blending and reframing in linear light and doing one tone-map to SDR at the very end gives better highlights and shadows and a consistent look across clips than Normal mode's baked-in curve.

### Ground-truth exports from DJI (user added 2026-09-30) and the stitch is now validated
Files: `videos/0930.mp4` and `videos/0930(1).mp4`. Both are 7680×3840 equirect HEVC Main **8-bit** (`yuv420p`, BT.709), constant **50 fps, 240 frames, 4.80 s** (the OSV has 239 frames over 4.82 s, so DJI filled the dropped frame by duplication), AAC audio, tagged equirectangular (`GSpherical`, stitching software "StitchCut"), about 189 MB each.
- **Their `CreateDate` is the export time (2026-09-30 06:26/06:27), not the recording time.** Never use exported files for timing; the OSV is the only time source. Also the frame count differs from the source.
- **`0930.mp4` is horizon-levelled / stabilised** (trees vertical, horizon flat, the user's head at the left edge, upright). **`0930(1).mp4` is the raw body-frame stitch** (camera tilted as filmed). PSNR between them is only 11 dB. So the DJI 360 export **does** apply horizon lock, and the user's "rocksteady disabled" export really is unstabilised. (`0930.mp4` is the target for our stabilisation step; `0930(1).mp4` for the stitch.)
- **Result: our own stitch from the file's calibration matches DJI's.** NCC vs `0930(1).mp4` (frames at t=0.5 s and 2.0 s, 1920×960, blurred grey): **0.972 and 0.982** for the correct convention. Every other convention scores near zero or negative (best wrong: 0.18). The correct one is:
  1. `d_lens = R(q)·d_body`, **not** transposed (transposed scores 0.10–0.18).
  2. **Video stream 0 is the rear (slave, slot 1) lens and stream 1 is the front (master, slot 2) lens.** (Assigning stream 0 as master scores negative.) This is the opposite of the intuitive guess.
  3. The refined slots (2, 1) beat the `native` slots (12, 11) slightly (0.982 vs 0.979).
  4. Standard equirect layout: centre column looks along +Y (front lens), lon increases to the right, lat up.
  5. Blend: smoothstep between 86° and 94° from each lens's axis (simple; DJI's is better near the seam).
- Residual vs DJI (t=2.0 s): mean abs difference 0.049 (0–1 scale), median 0.030, p95 0.17. It is concentrated at the **seam beside the user's hand** (band at lon −90°: 0.130, at +90°: 0.072; front centre 0.039), which is parallax that DJI corrects and we do not yet (OpenOSV's `searchSeam` does this too). Sharpness looked similar at this scale, not yet measured at full resolution.

Whole-image correlation against a reference is the right test. Kept `spike/stitch_eq.py` (equirect stitch + NCC) and `spike/osvcalib.py` (calibration reader) as the start of the real code.

### Gyro stabilisation validated against DJI's upright export (2026-09-30)
Method: match SIFT features between DJI's raw export (`0930(1).mp4`) and its upright export (`0930.mp4`) at 10 times (`spike/rot_est.py`, RANSAC-Kabsch on unit rays, 97%+ inliers each), giving the exact rotation DJI applied; then compare with the telemetry quaternions (`spike/telemetry.py`).
- **Telemetry:** per-frame attitude is `FrameMeta.2.9` (4 floats, unit norm); timestamp `FrameMeta.1.2` (device microseconds); there is one djmd packet per video frame, and the timestamps show the **same 60 ms gap at frame 29** as the video, so frames and telemetry align 1:1. Higher-rate batches (20 quaternions per frame) exist in `FrameMeta.3` but were not needed.
- **DJI applies the raw attitude and nothing else:** the rotation between any two moments in DJI's stabilised export equals the telemetry quaternion's relative rotation to within **0.1–0.2°** (e.g. 15.81° vs 15.90°, 31.24° vs 31.18°). So the export is full orientation lock (roll, pitch **and yaw**, no extra smoothing) in this "rocksteady off/on" export.
- **Simple conventions failed because of an IMU-to-lens mounting offset.** 24 combinations of quaternion order, rotation sense and world-up axis without an offset gave inconsistent winners (best NCC 0.57–0.73). Solving for constant matrices P and B fixed it: `R_ab(t) = P · R(q_t) · B`, mean error **0.097°** (max 0.22°). With the stored fields (1,2,3,4) read as **(w, x, y, z)**, `R = quat_to_R`. `B` is essentially an axis swap (x↔y, z flipped: about 179.4° rotation) between IMU and body/lens frame, and `P` a similar swap plus an arbitrary **yaw datum of about 9.4°** (DJI's choice; irrelevant to us). Stored in `scratchpad/PB.npy` for now (to be written to a per-camera config).
- **Model:** for an output direction `d_E` (upright, X right, Y forward, Z up), the body-frame direction is `d_body = Bᵀ · Rᵀ · Pᵀ · d_E`, then project through the lens calibration. `Rᵀ` with `Bᵀ` first means this is world-locked; to get a heading-following (roll/pitch-only) or a smoothed camera we modify `R` before applying it.
- **End-to-end check (held-out frames not used for the fit):** stitching upright straight from the raw fisheye frames with this model scores NCC **0.9932 (t=0.9 s), 0.9950 (1.7 s), 0.9983 (2.9 s), 0.9973 (4.2 s)** against DJI's upright export. The unstabilised body-frame stitch scores 0.06–0.33 on the same frames.
- **Implication:** we can do our own stabilisation exactly, and, because the quaternions are the only thing DJI uses, we can choose different behaviour: full world lock, roll/pitch-only horizon lock with a smoothed heading (probably better for a runner: a fully world-locked view spins away when the user turns), or heavy smoothing. This is what Phase 6 needs.

### Direct fisheye → 4K flat renderer (`spike/render4k.py`, 2026-09-30)
Design: for every output pixel build the view ray, rotate it into the camera body frame with the stabilisation matrix `M = Bᵀ Rᵀ Pᵀ` (from the telemetry quaternion), project through the two calibrated KB5 lenses, sample, and blend across the seam (smoothstep 86°–94° from the front-lens axis). **One resample per output pixel, no equirect stage.** The mapping is evaluated on a coarse grid (1/8 resolution) and upsampled with `cv2.resize`, then `cv2.remap` (bicubic) on each lens. Roll is levelled from gravity (the world-up direction in the body frame). Two modes so far: `body` (look along a fixed camera-body direction, e.g. at the user, with roll levelled) and `world` (a fixed direction in the stabilised world frame). Decode uses two ffmpeg processes with `-hwaccel videotoolbox` piping RGB24 at 3840×3840; encode uses `hevc_videotoolbox` Main 10 (80 Mbit) with `hvc1` tag, fed 8-bit RGB (the pipeline is 8-bit for now).
- **Speed (Apple M4, full clip, 4.82 s, 3840×2160 at 50 fps):** body-locked view at 100° FOV **14.5 fps (16.7 s)**, world-locked view at 90° FOV **10.3 fps (23.4 s)**. The world-locked view crosses the lens seam so both lenses are remapped and blended. Per-frame costs: read/decode about 29 ms, remap 35–64 ms, write 4 ms; the map calculation is negligible. So about 3–5× slower than real time in Python/OpenCV on the CPU; no GPU port needed yet. A 100-clip race of 30 s each (50 min of footage) would take roughly 3–4 hours; fine overnight, and there is headroom (threads, Metal, avoiding the RGB conversion).
- **Correctness:** the body-locked frame is a clean rectilinear 4K view of the user (with lens droplets rendered faithfully). The world-locked frames at t = 0.5, 2.5 and 4.4 s show the same scene (rocks, tree trunk) in the same position while the camera moves: the stabilisation works end to end in the renderer, not only in the equirect test.
- **Timing:** output is constant 50 fps; the source's 60 ms gap at frame 29 is **two dropped frames** (not one), so 239 source frames become 241 output frames (4.82 s, equal to the source duration). The dropped frames are filled by repeating the previous frame. DJI's own export has 240 frames (it handled the gap slightly differently).
- **Comparison with the ffmpeg `v360` route:** `v360` on the same clip was much slower (the earlier benchmark of 4K flat and 8K equirect renders each took long enough to hit the tool's 120 s timeout, no timings captured) and uses a generic FOV instead of the calibration. Superseded.
- **Known gaps / next:** (1) no audio in the render yet (mux from the OSV, and match the 241-frame duration); (2) seam parallax correction and exposure matching between lenses (our image is about 7% darker than DJI's); (3) 8-bit path (source is 10-bit; keep 10/16-bit through the render, per the colour policy); (4) camera paths: only fixed directions so far, no keyframed pan/zoom (Phase 6/7 will drive the same renderer with per-frame yaw/pitch/fov); (5) heading-follow stabilisation (roll/pitch lock with smoothed yaw) not yet implemented, only full world lock and body lock; (6) resample quality (bicubic vs Lanczos) and sharpness not compared with DJI at full resolution; (7) fisheye edge handling and the occlusion polygon (selfie stick side) are not used yet.

### Colour work: ported OpenOSV's photometric pipeline (2026-09-30, after the user asked to copy OpenOSV's techniques)
**What "colour is off" turned out to be.** Our first renders were about 5–13% darker than DJI's export. Measured over ten frames (linear light, DJI ÷ ours): front lens 1.05–1.13, rear lens 1.04–1.11, and the lift is **inversely related to how bright our frame is** (ours mean luma 0.36 → DJI +13%; ours 0.42 → +5%), and it does **not** track the exposure metadata (ISO×shutter is constant while the lift changes). So **DJI Studio applies a scene-adaptive brightness/tone lift to its exports; it is not a fixed gain or an error in our image.** OpenOSV treats a Normal-mode clip as "SDR in, SDR out: comes out as recorded, changed only by the stitch (gains, shading, exposure)" (docs/COLOR.md). Matching DJI's lift would mean imitating an undocumented adaptive filter. **Decision: render as recorded**, and do any look/exposure matching deliberately in Phase 7 (per-shot exposure matching, per the colour policy).

**Real bugs found and fixed while doing this:**
1. **Wrong RGB→YCbCr matrix and untagged output (affected every earlier render).** ffmpeg converts RGB to YUV with BT.601 by default and the file was untagged, so players assume BT.709 and show saturated colours wrong by up to ±36 levels (measured on colour patches; greys unaffected). Fixed: encoder now uses `scale=in_range=full:out_range=tv:out_color_matrix=bt709`, `-colorspace/-color_primaries/-color_trc bt709`, `-color_range tv`, and a `hevc_metadata` bitstream filter to write the VUI (VideoToolbox does not write transfer and primaries on its own). Verified with ffprobe: `bt709/bt709/bt709`, tv range, Main 10, `hvc1`.
2. **8-bit pipeline.** The source is 10-bit; our decode was 8-bit RGB. Now decodes to **16-bit RGB (`rgb48le`)** and stays 16-bit through remap, blend and encode (Main 10, `p010le`). Decode cost rose only about 0.5 s over the clip; the pipe (88 MB per lens frame) is now the main read cost.
3. **Blending in gamma space.** Now blended in **linear light** with the BT.709 transfer (OETF knee 0.018, inverse knee 0.081, 1.099·x^0.45−0.099, exactly as OpenOSV's `ColorMath.h`), via 65,536-entry LUTs.

**Ported from OpenOSV (`spike/photo.py`, `spike/render4k.py`; Apache-2.0, see `NOTICE`):**
- Lens weight = smoothstep FOV feather × **occlusion factor**. Analysis blend: half-FOV 97.59°, feather 4°, occlusion ramp 24 px. **Render blend is inset 2.6° (ends at 94.99°) with a 3° feather** (`PhotoSeam.h`).
- The **14-point occlusion polygon** from the calibration slot (fields 22 = x, 23 = y; same shape in both lenses: the selfie-stick footprint at the bottom of the image) as a distance-based mask.
- The **occlusion rescue** (where both weights vanish, a lens that landed in its FOV on an unoccluded pixel gets weight 1e-3, so no black holes).
- Weight normalisation, blending in linear light, conversion back with the same OETF.
- Exposure-match gain (`estimate_gain`): symmetric split (sqrt) of the trusted-pixel mean ratio in linear light, clamped to [0.5, 2], band ±6° around the seam, trusted = both lens weights ≥ 0.99, per bucket of 8 frames. **Implemented but off by default (`--gain off`).**

**Why the exposure-match gain is off:** on this clip it returns 1.6–1.9 (near the clamp) and 1.1–1.2 at another moment, i.e. nonsense, because at the seam the two lenses see different things: the user's hand and body at 0.5 m (large parallax), wet lenses with droplets and rainbow flare, sky glare. A robust per-pixel median gave ratios 1.2–2.5, and gating to structurally agreeing pixels (local NCC > 0.5–0.85) still gave 0.9–3.0 on only a few hundred pixels. OpenOSV's own later stage (the SSIM-gated photometric field) exists for this reason. DJI's own lens-to-lens difference in its export is only about 2% (front vs rear), so unity gain is within about 2% of correct here. **Metadata check:** the two exposure tracks give a 3.0% ISO×shutter difference (djmd3 1/500 vs djmd4 1/485 at ISO 801 vs 800, changing to 1/662 vs 1/643 mid-clip) which is the same order but did not track DJI's lens difference over time, so it was not used either.

**Speed after the changes (M4, 3840×2160, 16-bit, linear blend, full 4.82 s clip):** body-locked view **10.7 fps (22 s)**, world-locked view crossing the seam **5.0 fps (48 s)**. Optimisations that mattered: boolean-mask copies were 180 ms per frame, replaced by `cv2.copyTo` masked copies and integer-index gathers (render call 387 ms → 120 ms at the seam; 73 ms single-lens). The remap itself (bicubic on 16-bit) is only 14 ms; the 16-bit read is now 12–15 s of the total. The seam view is still the slow case.

**Colour accuracy check:** rendering the front-lens axis view and comparing broad rings around the axis with the same region of the source frame: mean RGB ratios 1.00 (150–400 px ring), 0.98–0.99 (400–700 px), 1.01–1.05 for the small central ring (content and rotation differences). So the pipeline reproduces the recorded colours to within about 2% (as recorded, no lift).

| Seam disparity search (`searchSeam`) + 1-D seam shift | close objects at the seam | measured per column, per bucket |
| Parallax warp (DIS optical flow, `ParallaxWarp`) | 2-D correction of parallax in the seam band | biggest visible gain for the hand next to the lens |
| Carved seam (DP seam carving, `SeamCarve`) | choose where the lenses meet | avoids cutting through faces and hands |
| Photometric seam field (`PhotoSeam`) | rim-aware weights, 2-D log-gain field, SSIM-gated | the proper fix for the lens gain mismatch on this kind of footage |
| Lens shading correction (`LensShading`) | additive rim veiling glare | per lens, from sky |
| Flare removal (`Flare`) | sun ghosts | probably not needed for this clip |
| Two-band seam smoothing (`SeamTools`) | glide the low-band difference across a wide band | cosmetic |
| Clip-steady mode (`ClipSteady`) | one correction per clip instead of per bucket | reduces seam wobble on rigid mounts (not applicable to a hand-held stick) |
| D-Log M / HLG decoding and looks | non-Normal colour modes | only needed if the user shoots D-Log M |

### LRF vs our own proxy; proxy and encoder studies (2026-09-30)
**Question (user):** use the camera's low-res `.LRF` as the proxy, or make our own? Also: should the proxy be a clip or individual frames, at what bitrate and fps, and can one file serve all visual analysis? Plus the constraint (user): *the DJI quality is not amazing, so preserve as much of it as we can.*

**Facts about the LRF (sample):** 2048×1024 H.264 High, 7.84 Mbit/s, 8-bit, tv/BT.709, showing the **two fisheye circles side by side** (about 1024 px per lens, 0.27 of source scale, roughly 5 px/°), 25 fps, 120 frames over 4.80 s with one 80 ms gap (a dropped frame), timestamps identical to OSV frame times (mean |dt| = 0.0000 s). **It is frame-synchronous with the OSV:** the correlation between an LRF-based render and an OSV render peaks at offset 0 (0.998–0.999; 0.952–0.954 at ±1 frame, 0.85–0.91 at ±3). (An earlier apparent offset was an artefact of `-ss` seeking in my comparison.) Through the same pipeline at 1920×960 it correlates 0.929–0.972 with DJI's upright export versus 0.970–0.980 for our full-resolution render, and it keeps about **half the fine detail** (Laplacian variance 0.00054–0.00068 vs 0.0012–0.0014 for ours and 0.0008–0.0009 for DJI's own export). Also carries djmd tracks (120 packets) and audio.

**Decision:** the LRF is **not** the canonical proxy: it is soft, 8-bit H.264 at 7.8 Mbit/s, dual-fisheye (we need our own projection anyway), and other cameras' proxies differ. Cheaper versions are derived from it on the fly. **Recognition detail comes from source crops, never from the proxy.**

**Proxy generator results (sample, whole clip):** 25 fps version: 120 frames in 16.7 s, 15.8 MB (26 Mbit/s requested 25M); correlation with DJI's upright export **0.973–0.987** at six times (small loss from the nominal-timestamp drift after dropped frames; the sidecar times are authoritative). Default 12.5 fps at 80M: 60 frames in 8.0 s, 49 MB (82 Mbit/s), about 10 MB/s of footage, about 37 GB per hour of footage (large for a "proxy"; tunable, provisional). Upright means its yaw datum equals DJI's upright export.

### Word timestamps for edit points (user: "crucial when deciding edit points"), 2026-09-30
**What the existing transcripts showed.** 596 words across 74 non-suspect segments: median word duration 200 ms but p95 765 ms and maximum 2,940 ms; **461 of 596 words (77%) have exactly zero gap to the next word**, 10 words have zero length. So whisper's word ends stretch over the pause that follows them.
**Ground-truth test (`spike/test_wordtimes.py`).** Each word is synthesised on its own (macOS `say`), trimmed to its audible extent (35 dB below its peak), and joined with known gaps (0, 0, 40, 100, 200 ms), so every true boundary is known; clean, real wind (+9 dB) and real babble (+3 dB), 52-54 words per condition, transcribed with large-v3-turbo.
| Method | start median / p95 error | end median / p95 error | within 40 ms | bias |
|---|---|---|---|---|
| whisper word times | 165-195 / 435-500 ms | 118-125 / 220-237 ms | 2-8% | **early by 120-190 ms** |
| CTC forced alignment (wav2vec2-base-960h) | 47-60 / 137-171 ms | 113-125 / 185-206 ms | 0-42% | starts late ~50 ms, ends early ~115 ms |
| CTC + energy refinement | 25-55 / 116-127 ms | 27-35 / 85-107 ms | 37-65% | starts -5 to -53 ms (noise), ends -18 to -28 ms |
**Cut points** (cuts chosen at each gap; "in pause" = inside the true pause, "inside word" = more than 10 ms into a true word):
| Condition | whisper times | CTC + VAD pause detection |
|---|---|---|
| clean, real pauses (32) | in pause 16%, **inside word 84%** | in pause **100%**, inside word 0%, 59% flagged safe |
| wind +9 dB (31) | in pause 3%, inside word 97% | in pause 87%, inside word 13%, 48% flagged safe |
| babble +3 dB (26) | in pause 19%, inside word 77% | in pause 62%, inside word 31%, 12% flagged safe |
| touching words (15-17 per condition) | never near the seam | **flagged safe 0% in all three conditions** |
First attempt (energy-only pause detection, no VAD): clean 100%, wind 74%, babble 54% in pause, but touching seams were flagged safe 93% of the time in clean audio (a real hazard: CTC word ends are early, which creates artificial gaps) and safe flags collapsed in noise. **Adding Silero VAD probability** (bundled with faster-whisper, 32 ms windows) to define a pause fixed both. Energy refinement improves boundary error but slightly worsens cut placement (cuts inside a word 12% clean), so cut placement uses the CTC times with VAD, and refinement is kept for in/out points.
**On the real library** (`align` over 1,557 English words, 1,381 gaps): only **12% of gaps are safe cut points** (natural speech rarely pauses between words); aligned-minus-whisper start median +30 ms (p10 -210, p90 +180), end +36 ms; aligned word durations median 220 ms, p95 540 ms, maximum 1,762 ms (whisper's maximum was 2,940 ms). A real segment showed the failure mode the gate exists for: "one um the last one lost my mind basically overnight um" had its first four words 500-900 ms early (the aligner struggles with the filler "um"); added the consistency gate (aligned start within 0.4 s of whisper's, aligner confidence at least 0.25) that marks words `ok: false` and prevents safe cuts next to them.
**Limits:** English only (French, Dutch and German need 1.2 GB wav2vec2 models each), synthetic isolated words (unnaturally clear boundaries), no test on real speech with hand-marked boundaries yet (a small labelled set from the library is the next step), and wav2vec2's character emissions are peaky, which biases ends early.

### Audio: analysis, conditioning chains, mix planner (2026-09-30, user's three use cases)
**Use cases (user):** (1) general background noise, kept under music and **swelled up during silence in the music**; (2) crowd, excitement and multiple people (start and finish): **normalise, no clipping**, in the mix where appropriate; (3) **quiet or muffled voice to camera by the user: noise reduction and auto-gain for the best speech recognition**.
**What the sample audio is:** AAC 48 kHz stereo 317 kbit/s, **dual mono** (both channels identical, so no stereo cues), 4.82 s, **−23.5 LUFS integrated** (my BS.1770 implementation gives −23.48, true peak −0.01 dBFS, both match ffmpeg's ebur128), sample peak −0.12 dBFS with no clipping, loudness range 6.6 LU. Spectrogram: dominated by 20–300 Hz wind and handling noise; a loud transient in the first 0.5 s; DJI's own processing gates energy above about 9 kHz between 0.7 and 2.2 s; **no clear voiced speech** (voicing 0–6%, so the wearer is not speaking to camera in this clip), consistent with the group of hikers heard behind. Labels from `analyse`: crowd (0.15–0.55 s transient, and 2.4–4.65 s the group's chatter, unvoiced, speech-band), ambience between.
**Code:** `spike/audio.py` (analysis, `enhance_speech`, `condition_ambience`, `mix_plan`, `render_mix`, `stoi_approx`), `spike/test_audio.py` (**10 tests, all pass**), `spike/example_audio.json`.
**Test method, since the sample has no speech:** speech with a known transcript from macOS `say` (offline), buried in the clip's own real noise at controlled speech-band SNR (−10 to +10 dB), plus synthetic timelines (speech, rumble, near-silence, six overlapping voices) and synthetic music for the mix logic.
**Findings and dead ends (in order):**
1. **SI-SDR is the wrong metric here.** With it, even a plain 100 Hz high-pass "lowered" the score by 2–5 dB, and the full chain looked much worse than doing nothing. Cause: SI-SDR compares waveforms, so it punishes the phase delay of every filter and any time-varying auto-gain (both irrelevant to recognition). Gain-invariant per-frame SI-SDR did not fix it. Dropped.
2. **STOI (short-time objective intelligibility) is phase-insensitive**; I implemented a compact version (`stoi_approx`; sanity: clean 1.000, white noise 0 dB 0.939, −10 dB 0.764). Caveat: like real STOI it is blind to linear filtering (a 500 Hz low-pass scores 0.998), so it measures noise contamination only, which is what a denoiser should improve.
3. **Result: classical ffmpeg denoising barely changes intelligibility on this real noise** (wind plus people talking nearby). STOI at speech-band SNR −5 / 0 / +5 dB: input 0.718 / 0.841 / 0.922; with afftdn 0.725 / 0.846 / 0.923; the full chain (high-pass, afftdn, EQ, speech-normalise, limiter) 0.722 / 0.840 / 0.919. `anlmdn` gave no gain. So the chain is guaranteed safe (never worse by more than 0.005 at +10 dB), levelled and clip-free, but not a real noise remover. Real improvement needs a neural denoiser and an ASR to measure with (**not installed; awaiting permission**).
4. **Numpy matmul is broken on this Mac** (warnings, then suspect numbers). The STOI band-sum used `@` and flooded the log with warnings; switched to `einsum` (results unchanged, so no corruption in that case). Third time this has bitten; every numeric module should avoid `@` on large arrays, or numpy should be reinstalled with a working BLAS.
5. **Crowd rule bug:** my first crowd test required more than 4% energy above 3.4 kHz, which synthetic voices lack; replaced with "energy concentrated in the speech band (at least 30%) but not one clean voice, and not wind". Classification on the synthetic timeline: speech 65%, wind 100%, silence 100%, crowd 100%.
6. **Mix loudness vs limiter:** the −18 LUFS speech target came out −20.3 LUFS at low SNR because the peak limiter takes loudness back; now iterates up to three times to converge (−18.0 to −18.3).
**Mix planner (verified on synthetic music):** ambience swell +12 dB in a 2 s gap (rises 0.5 s, drops 0.15 s when music returns, ignores a 0.2 s rest); music ducks −12 dB for speech and −6 dB for crowd; final mix peak-safe (no clipped samples, true peak −4.2 dBFS on the test) and on loudness target (−16.0 LUFS).
**Quiet voice check:** a −45 dBFS voice is lifted to above −30 dBFS RMS while room tone stays more than 25 dB below it (the speech-normaliser's threshold keeps pauses from being boosted).
**Next (needs a decision):** install faster-whisper (or whisper.cpp) and a neural denoiser (DeepFilterNet or RNNoise), both downloads, to measure word error rate and get real noise removal.

## Is gyro stabilisation enough? Measured residual jitter (30 Sep)
- Test: clip 0021 (the shakiest, steadiness 0.17, median shake 44 deg/s), seconds 10-20, forward view 100 degrees, 1280x720. Global image motion between frames measured by phase correlation on the rendered output (jitter = motion faster than 0.5 s):
  - body-locked (no stabilisation): rms jitter 5.8 deg horizontal, 9.4 deg vertical, frame-to-frame 5.5 deg.
  - world-locked (gyro horizon lock): 0.27 / 0.09 deg, frame-to-frame 0.06 deg.
  - heading-follow (world lock plus smoothed heading): 0.15 / 0.11 deg, frame-to-frame 0.05 deg.
- So rotation stabilisation removes about 98% of the shake; what remains (about 0.1 deg, about 4 px at 4K) is mostly real camera translation (running bounce, parallax) plus measurement noise. Rotation cannot fix translation; video-based stabilisation would fight parallax and add warping, so it is not worth it.
- Where motion data can still help is the choice of view, not shake: adaptive heading-follow smoothing (longer in straights, shorter in bends, look-ahead into turns), subject lock for selfie framing (from the people stage), and steadiness/cadence as selection features (already in motion.json). Possible small gains: rolling-shutter correction and per-frame gyro-video sync check.

## Selfie stick removal: the occlusion mask was wrong
- OpenOSV (geom/LensRig.cpp buildOcclusion): the calibration stores the stick as an OPEN ARC of 14 points near the bottom rim of each lens (apex twice, in an order that does not trace the arc). The occluded region is the thin sliver between the arc and the edge of the image circle (the stick enters from outside the frame): sort the arc by angle about the lens centre and close it OUTWARD along the rim; the other lens then fills in behind the stick (its occlusion rescue keeps the stick region at zero in the blind lens).
- We filled the stored points as they are (`render/photo.py occlusion_map`): 3.7% of the frame in the wrong place instead of the 2.0% sliver. Result: the pole showed as a dark band when looking down, with black holes with jagged edges beside it where good picture was masked and the other lens could not fill in.
- Fixed: `photo.occlusion_polygon` (angular order, closed to the rim at theta 97.59 deg), used by the renderer (flat/proxy/final) and the exposure analyser; `Lens.rim_radius`. Test: tests/unit/test_occlusion.py. Before/after views looking along the pole: the pole and the voids are gone.
- Proxy stage version 3 -> 4: existing proxies still show the pole until re-rendered. The final render (from the lens video) already uses the fix. Not done: OpenOSV's further steps for near objects (optical-flow seam, DP seam carving through places the lenses agree; DJI also runs a learned stick mask), exposure re-run.

## Carved seam between the lenses (hands and other near objects poking in)
- Cause: something a few centimetres from the camera (the hand on the grip, the pole, near branches) is seen from two viewpoints about 3 cm apart; the default blend (a field-of-view feather: both lenses at 50% across the overlap) shows BOTH copies (ghost, doubled hand) or cuts the object.
- `render/seam.py` (port of the idea in OpenOSV SeamCarve): both lenses are sampled into the overlap band (polar-axis strip, +-9 deg of latitude, 2048 columns); a cost per seam position (the lenses' disagreement in a 0.35 deg window, blind areas (the stick mask, past the field of view) forbidden, partial coverage penalised, a gentle pull to the equator, a hold on the previous frame's seam and a 2 deg clamp); a closed-ring DP along longitude (max 2 rows between columns); smoothing; a feather per column: 1.5 deg where the lenses agree structurally, 0.35 deg where they do not. The renderer uses one lens on each side of the seam (`Renderer.update_seam`, `carve_seam`), the other fills in where one cannot see.
- On by default for the proxy, the final render and `flat.py` (`--seam off` for the old blend). 60 ms a frame; the seam moves 0.001 deg between frames with the hold (0.1 deg without). The hand on the grip: the doubled, blurred hand and the grey ghost across it are gone; near branches are sharper. Trade-off as in OpenOSV: where something straddles the seam a faint cut edge can show. Tests: tests/test_seam.py. Proxy stage version 5.
- Not done: OpenOSV's optical-flow parallax warp (a 2-D grid that moves each lens toward the other before the seam) and its learned stick mask.

## Parallax warp (optical flow between the lenses)
- `render/parallax.py` (port of the idea in OpenOSV ParallaxWarp): DIS optical flow between the two lenses in the overlap band (forward and backward, kept where they agree and both lenses see), the median flow per cell of a 256 x 32 grid, empty cells filled from neighbours, smoothed (harder across the meridian), faded to zero at the band edge, then a benefit gate (a cell keeps its correction only if warping both lenses by it cuts their disagreement by 20%+). Each lens is sampled at the direction displaced by half the disparity, in opposite directions (`Renderer.warp`, `Warp.apply`); the seam is carved through the corrected bands. 25 ms a frame; averaged with the previous frame's grid.
- Measured: the lens-to-lens disagreement in the overlap falls 36-54% (e.g. 0.085 -> 0.039) on four of five test frames; a clip with too little texture gets no warp.
- A first version smeared and doubled the HAND (a near object: the gate did not stop it). Fix: a cell whose disparity is over 1 degree is a near object (a hand at 30 cm has about 6 degrees; calibration error and far parallax are under 1), left to the seam; the warp is the smooth far-field part only (max correction 0.95 degrees). After it the hand stays sharp.
- On by default (proxy, final, flat `--parallax off`). Proxy version 6. Tests: tests/test_parallax.py.

## Per-area quality spike: what the proxy alone can and cannot tell us (1 Oct 2026)
- Scripts: `scripts/quality_spike.py` (15 degree grid, 2 Hz, from the equirect proxy: fine and mid detail, blur ratio, texture, dark channel, contrast, saturation, clipping) and `scripts/quality_persist_spike.py` (rotates each frame into the body frame with the gyro; looks for areas featureless in the body frame over a window although the world passing through them is not). Tried on clip 0018 (water drops and a smear on the lens, VLM-flagged at 25 to 90 s, clean at 5 to 20 s).
- **Plain per-cell texture and blur do not find lens contamination.** They flag distance haze and sky (real scene content) and count about the same cells on clean and wet moments (18 vs 21). Droplets are also smaller than a 15 degree cell.
- **Body-frame persistence works while the camera moves**: at 25 s it lit up the vertical water smear exactly, with no false hit on sky or haze. It is blind when the camera stands still (clip 0018 stops at a stream from about 55 to 90 s: the big streaks and drops there were missed), needs a window long enough for the camera to turn (10 s gave 10 to 25 degrees), and misses faint round drops.
- The stick (an old v3 proxy artefact here) also shows up, as it should: it is fixed in the body frame.
- Next to try: the local VLM (Qwen2.5-VL 3B, already in `scenes`) asked for boxes of drops, smears, fingers and fog on each lens view, combined with the persistence map to locate and confirm; and the saved seam disparity grid from the proxy render for near objects. Not run: the VLM needs about 3 to 4 GB while the batch is rendering proxies.
- **Proxy cost seen:** clip 0001 (12 s) took 358 s to render with the seam and parallax warp on a busy machine, about 30 s per second of footage: roughly 10 hours for all 1,240 s.


## Scenic prompt experiment: graded score works, pairwise does not (1 Oct 2026)
- Old `scenic` (scenes stage) is nearly binary: of 407 answers 335 are 0.7 and 72 are 0.0 (indoor, aid station, night), so it flags "no scenery" but cannot rank two good views; front and rear agree 75% of the time (both >= 0.6), both bad 14%, differ by 0.3 or more only 12%. A pure black frame was scored 0.8.
- Simple measures on the 15 degree grid (`scripts/quality_spike.py`, `scripts/view_pick_spike.py corr`) against those answers: detail and flat share barely correlate with scenic (rho +0.03 / -0.10), moderately with the VLM's `energy` (0.30 / -0.34). They separate fog clearly (fog-flagged views: score 0.08 vs 0.44, flat share 67% vs 26%) but punish open, smooth, beautiful landscapes (fields: scenic 0.69, simple score 0.16) and reward busy places (aid stations). So: use them as guardrails (exposure, heavy fog), never to rank.
- New prompts tried on 33 moments (66 views, 8 clips; `scripts/vlm_exp/`): a **graded 1-10 score with anchor descriptions plus a 1-5 clarity** gives 1/2/3/5/6 (3/8/8/11/35 of 65 answers), scores the black frames 1-2, and on the six biggest front-vs-rear gaps always prefers the clear view over the foggy one (agrees with the eye). It never goes above 6, so ties on good footage remain. The wearer is in most rear views and may be pulling "clear subject" up; not separated yet.
- **A pairwise "which is better" prompt (both orders) is useless on the 3B model**: it answers "A" in 26 of 33 whatever the order and agrees with itself after swapping in only 6 of 33. Dropped.
- Cost: about 5 s per answer; front + rear graded every 5 s is about 40 minutes for all of Legends.
- To do: promote the graded prompt (with `clarity`) into the scenes stage (version bump), re-run after the proxy batch, and build the per-clip quality timeline from front, rear and the guardrails.
- **Scenery-only prompt (people ignored, `scripts/vlm_exp/run_scenery.py`), same 33 moments:** the score distribution is almost the same as the first graded prompt (mean front/rear 4.67 / 5.09 against 4.45 / 5.03; values 2 to 7, mostly 5 and 6), the front-rear gap is slightly smaller (mean 0.88 against 1.06), and the direction of the big gaps is kept (7 of 8 same sign). So the "clear subject" wording was not inflating the rear views (the wearer) much; removing it is cleaner, since the people stage already knows about people. It slightly lifts non-person scenery (a chateau 6 to 7) and slightly lowers its fog penalty (one foggy front 3 to 5, clarity 3 to 4), so keep `clarity` as a separate field and the fog guardrail from the grid. Still coarse: use scenic as bad / fine / good plus a direction where the gap is 2 or more, not as a fine ranking.

## Design decisions and learnings, 1 to 2 Oct 2026 (session summary)
- **Proxy:** the v6 proxy crashed on every clip (`EquirectRenderer.maps` never set `_dirs`, which the carved seam needs, and skipped the parallax warp): fixed with a unit test that fails without it; the first v6 clips look clean. The renderer is CPU only (numpy and OpenCV); the GPU is used for video decode and encode. About 30 s of rendering per second of footage on a busy machine, at nice 19 with 2 threads: about 10 hours for all of Legends. The worker's busy gate is the 1-minute load average over 80% of the CPUs; a second worker needs 7 GB of memory available (the default was 12 GB, never reachable on this 16 GB Mac). `strata360 run` and `strata360 open` now refuse to start a worker that would break the limits (the app already did).
- **A cache fact worth remembering:** a stage key is its version, the clip file, its config keys and the key of the stages it depends on. The camera clock does not invalidate anything (ingest's key is frozen), and a stage that depends on the proxy only softly (people, scenes, thumbnails) keeps its results when the proxy is re-rendered.
- **Quality signals:** plain per-area texture and blur do not find lens contamination (fog and sky look the same); body-frame persistence found a smear while the camera moved and nothing while it stood still. The user's steer: quality is a soft score, large flat patches matter only above about 10 to 25% of the view, droplets are not worth chasing. The VLM's graded scenery score (not the old yes/no) plus the exposure and fog guardrails is the plan. A pairwise "which is better" prompt does not work on the 3B model (answers "A" in 26 of 33 whatever the order).
- **The rough plan found the speech problem:** treating every speech stretch as must-carry dialogue is 228 s on Legends against a 247 s film. Hence V2b: the script writer chooses, the user steers by marks and pins, and the script's clip items become the dialogue.
- **Writer experiment:** the prompt matters less than the facts it is given (the track length and duration read as race distance and time limit; the notes already carry the story beats). Hard grounding rules cut good narration, so grounding is advisory; structure (length, order, pins) is checked in code with a retry, and the model's own arithmetic is never trusted. One Gemini 3.1 Pro call costs about 5 to 10 cents.
- **Process:** two of my "errors" were my own checker's (GPS length used as the race distance); check a claimed error against the source before reporting it. A trained scenic model would overfit one race: the VLM stays the signal.
- **3D flyover (2 Oct):** MapLibre Native's terrain branch renders on Metal here, so the flyover uses it, not GL JS in a browser (supersedes the earlier plan in N2); the camera findings (screen-space heading fit, panning instead of rotating, pitch falling with zoom) are in `docs/terrain-flyover.md`. Not yet connected to the film.
- **Gap clips (2 Oct):** a generated clip is an ordinary plan window whose picture is an MP4 (`render/synthetic.py`); the 2D map clip has its own overlay baked in at its speed-up, so the film render needs no time map. Gap ids depend on the minimum length used to find them (`--min-minutes`), so the clip command takes the same value.
- **Failing quietly hid a defect:** with no Thunderforest key the thumbnail overlay silently left the maps out for all 25 clips until the user noticed. A missing key is now an error everywhere; do not add "skip and carry on" fallbacks for missing configuration.
- **A bad merge on main (2 Oct):** a test-only PR (d5545ef) deleted merged work (the script writer, transcript marks, their tests). When a merge shows deletions of files nobody meant to remove, keep this side's tree and take only the genuinely new files.
- **Windows paths:** a path built with `os.path.join` from a relative `a/b` part mixes separators; normalise (`os.path.normpath`) before comparing or storing.
- **3D flyover in the app (2 Oct):** the prototype is `overlay/flyover.py`, a `flyover` kind of generated clip (4K), `gap-clip --kind flyover` and a per-gap *2D map / 3D flyover* dropdown. Camera and style are unit tested with `mbgl-render` faked, and it runs for real on Linux too (built from the terrain branch, Mesa software GL, 4K clip encoded); sharp tiles are the default. Windows is still to try.

## Project metadata backups

`pipeline/backup.py`: `<project>/backups/meta-<UTC>.tar.gz`, at most every 30 min and only if the fingerprint (path, size, mtime) of the saved files changed. Everything in the project is saved except media/images/logs/locks/temp files and files over 5 MB, so new data files are included automatically. Retention is exponential (3 h all, hourly to 1 day, daily to 1 week, weekly to 5 weeks, monthly to 13 months, then yearly). Runs from the server (projects it has opened) and from every pipeline worker; `strata360 backup FOLDER [--list|--restore NAME [--to DIR]]`. Not saved: recorded voice-over audio (media), the secrets file is a project-external file.
