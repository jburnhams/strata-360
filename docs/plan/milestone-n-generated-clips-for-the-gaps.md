## Milestone N: generated clips for the gaps (idea 2 Oct; research done, decisions open)

Long stretches of the race have no footage: most nights, and the hours when the runner could not face a camera. They are where narration is most wanted and picture is missing. Idea: **make clips for the gaps**: bird's-eye flights along the GPS track over the terrain, very fast for a whole gap (an hour or more becomes a few seconds to tens of seconds), plus **slower versions of a chosen stretch on demand** where a detailed voice-over needs picture. They enter the auto edit like any other clip.

**What the research found (2 Oct), and what it rules out:**
- *Google Aerial View API:* US postal addresses only, built for buildings and landmarks, not routes ([overview](https://developers.google.com/maps/documentation/aerial-view/overview)). Not usable for Belgium or for a route.
- *Google Photorealistic 3D Tiles (Map Tiles API):* the policies forbid pre-fetching, storing or caching tiles and any "non-visualization" or offline use, and allow recorded video only as a promotional video of an application you built, at most 30 seconds, marked "for promotional purposes only" ([policies](https://developers.google.com/maps/documentation/tile/policies)); customers with an EEA billing address have different terms. Rendering our own flyover film from these tiles is not permitted, so an API key does not solve it.
- *Google Earth Studio* (the web animation tool, KML import works for moderately sized files): no licence for commercial use, "Google Earth" and the data providers must be on screen for the whole duration of the content, and the FAQ mentions no API or scripting ([FAQ](https://www.google.com/earth/studio/faq/)). Usable for a personal, non-commercial film with a watermark, with a manual render step per flyover; not automatable.

**Options (cheapest first):**
1. **N1: an animated 2D map clip made with our own overlay code (decided 2 Oct: first, before any 3D).** No licence question, automatable, deterministic, and the code exists: `overlay/` already draws the clock, distance, pace, altitude, slope and heart rate from the track at any UTC (`series.py`), the whole-route map with a marker, the moving close-up map with automatic zoom (`zoom.py`), over cached tiles (`tiles.py`), with Pillow and OpenCV (5 ms a frame at 1080, 22 ms at 4K). A map clip is those pieces arranged for a whole frame: the close-up map fills the frame and follows the position; the route behind is bright and the route ahead dim; a position marker; the elevation profile along the bottom filling in as the clip runs; the whole-route inset with a progress dot; the clock, distance and pace.
   - **Time and speed:** frame *k* shows UTC `t0 + k * speedup / fps` (the speed-up is the gap's length over the seconds it gets in the film); the zoom follows the *speed on screen*, so the map zooms out when the camera would race across it, and the marker never moves more than a set number of pixels a frame; the position is smoothed.
   - **Pieces:** `gps/gaps.py` (the gap finder: spans between consecutive clips that lie on the track and are longer than a threshold [20 minutes]; for each gap the km range, elapsed time, climb, the share of it spent moving, daylight at each end, the clips either side); `edit/synthetic.py` (the synthetic clips file `synthetic.json`: id `G01`..., kind `map`, start and end UTC, speed-up, seconds, style, key, file, status); `overlay/mapclip.py` (the frame renderer) and a command `strata360 gap-clip FOLDER --gap G01 [--seconds S | --speedup X] [--from T --to T]` that renders to an MP4 with `hw.py`'s encoder (the final film's source for that window is then an ordinary 2D video: see "rendering needs a flat source" below); `strata360 gaps FOLDER` lists the gaps.
   - **Alternative renderer for N1 (idea 3 Oct):** the user's `leaflet-node` library renders a real Leaflet map to PNG on the server (jsdom plus `@napi-rs/canvas`, tile layers, polylines, markers, divIcons and Leaflet plugins work; ([repository](https://github.com/jburnhams/leaflet-node))). A Node script could draw each frame with the same map and styling as the in-app map and pipe the PNGs to ffmpeg, with our tiles served from the cache. It would be slower per frame than the Pillow overlay code and adds Node to the render pipeline, so the overlay code stays the first choice; worth a benchmark before deciding. It could also replace the hand-made jsdom stubs in the Leaflet component tests (`web/tests/utils/media.ts stubLayout`).
   - **Steps:** N1a the gap finder, the synthetic clips file and `gaps` (pure Python, unit tested); N1b the frame renderer and `gap-clip`; N1c the flat-source window in the film render and the time map; N1d the script pack and planner treat synthetic clips as clips (labels such as `G01`; the writer is told "no footage: generated map"); N1e the GUI (a gaps list, generate and slower variants on demand, a stretch chosen on the map or chart of Milestone M).
   - **N1b done:** `overlay/mapclip.py` (`MapClip`, `render`) and `strata360 gap-clip FOLDER --gap G03 [--seconds|--speedup] [--from --to --id] [--size --fps --style]` write `<project>/synthetic/<id>.mp4` and mark the clip `ready` in `synthetic.json`. Frame k shows `t0 + k*speedup/fps`; the camera follows the runner, zoom set so the marker moves ~0.4% of the frame width a frame; the stretch's route red behind and white ahead; elevation strip with cursor; the overlay's clock, distance, pace and whole-route inset on top. Defaults to Thunderforest landscape and fails loudly without a key (`--style osm` picks the key-free map on purpose); a missing key is an error everywhere (thumbnail overlay, final film, gap clips), never a quiet change of map or a map left out. Checked on Legends G03 (1.3 h in 6 s). Gap ids depend on `--min-minutes` (default 20), as in `gaps`.
   - **N1c/N1d done:** a generated clip is a plan window with `synthetic` = its MP4; `render/synthetic.py` plays it in the preview and the final render with no lens and no overlay in the clip itself: the final render puts the film's OWN overlay on it (the same elements and layout as on every camera shot, so the overlay does not change for gaps; user decision 3 Oct) at the race time each frame shows (`synthetic.race_time`: the clip covers `utc_start` to `utc_end` in `synthetic_seconds` of film). No credits are drawn anywhere (user decision 3 Oct): the overlay's `credit` element is off by default (it can still be added to `elements`), and `strata360 credits FOLDER [--write]` lists the credits the film needs (the overlay's map styles, the 2D maps' style, a flyover's imagery and terrain) for the film's distribution. The overlay also has an elevation profile of the whole race along the bottom with the runner's place on it (`profile` element, 120 reference pixels; the bottom row of numbers sits above it), the same on every shot. The script pack lists rendered generated clips as clips labelled `G03` (`SP.norm_label` replaces the `zfill(4)` label rule everywhere), marked NO FOOTAGE, with no words; they are optional for the writer (the 'every clip used or skipped' check ignores them) and are used as `broll` (whole clip) or under `vo`. `script_plan.build` places them between the footage windows (shifting later windows and voice lines), `project.insert_synthetic` writes them into the plan, `framing.resolve` skips them. Still open for N1c: audio of a generated window is silence (music and voice-over only).
   - **Done when (N1a):** unit tests on a synthetic track and clips: gaps are the spans between clips on the track longer than the threshold, overlapping clips merge, spans outside the track are not gaps, the moving share and km range are right, ids are stable for the same clips. **(N1b):** a rendered clip shows the right position at three known moments and its clock runs at the speed-up; no frame moves the marker more than the pixel limit.
2. **N2: a 3D terrain flyover with MapLibre Native (built as a prototype 2 Oct; the camera approved by the user; see `docs/terrain-flyover.md`).** This **supersedes the earlier plan** ("MapLibre GL JS in headless Chromium now, Native when terrain ships"): Native's `feature/terrain-3d` branch (draft [PR 4190](https://github.com/maplibre/maplibre-native/pull/4190)) builds and renders terrain on Metal here, with no browser and no WebGL-in-headless question. `scripts/flyover/render.py` draws one still per call with `mbgl-render` from a tile cache (`~/.strata360/flyover-cache.db`) and pipes the frames into ffmpeg (about 0.4 s a frame at 720p, run at `nice 19`, one process at a time). **Built:** Esri World Imagery over Mapterhorn terrain; a keyframed camera (zoom and pitch by speed; presets `fast`, `medium`, `slow`, `dive`, or a shots file); the heading fitted on the screen so the route stays in the picture and barely rotates (smoothed, dead-banded), the look-at point panning instead; a terrain-draped arrow marker. **Productionised (2 Oct):** `overlay/flyover.py` (`FlyoverClip`, plan_shots turns a gap into the camera, then the approved camera), `kind: flyover` in `edit/synthetic.py` (4K by default, `size` in the clip and its key), `gap-clip --kind flyover [--size --imagery --no-sharp]`, `kind` and `flyover.available` in the gaps API, a *2D map / 3D flyover (4K)* dropdown per gap in the Gaps panel, unit and web tests; it enters the film as the N1 map clip does. `scripts/flyover/` is removed. **Verified on Linux/OpenGL as well as the Mac (2 Oct):** `mbgl-render` builds and renders on Linux (Mesa software GL under `xvfb-run`), 4K frames and a 4K H.264 clip; sharp tiles are the default (crisper than enlarging 720p tiles, same framing). **Unverified:** Windows, 4K speed on the M4. **Not built:** the route line filling in progressively, and the imagery licence (unread for Esri, Sentinel-2 and the Wallonia orthophotos; needed before any shared film). The engine-independence idea (a style plus a per-frame camera list) is kept as a design goal, not a requirement: the prototype's camera is Python keyframes that the driver turns into `mbgl-render` calls. The decision history follows.
   **Engines considered for N2 (all open source; checked 2 Oct):**
   - **MapLibre GL JS** (BSD; the default pick): the lightest, terrain from raster-dem tiles (Terrain-RGB, easy to make and self-host from an open DEM with `rio-rgbify`), any imagery as XYZ tiles, a camera API, and an existing video-export plugin ([maplibre-gl-video-export](https://github.com/bjperson/maplibre-gl-video-export): deterministic per-frame capture, WebCodecs WebM, up to 4K). Plainest data path.
   - **CesiumJS** (Apache-2.0, free for commercial and non-commercial use; the real rival): a true 3D globe with terrain, 3D Tiles, atmosphere. A GPX flyover already exists as an open-source package ([`@geoblocks/cesium-path-flyover`](https://github.com/geoblocks/cesium-helpers/pull/186): drapes the track on the terrain, chase camera with a sample every 20 m, heading from a 400 m window with damping and rate limiting) and so does a frame-by-frame MP4 export with WebCodecs and no ffmpeg ([PR 197](https://github.com/geoblocks/cesium-helpers/pull/197)). Weaker on self-hosted open data (quantized-mesh terrain is more awkward to build than Terrain-RGB); its easy data comes from the commercial Cesium ion, whose terms are not read yet.
   - **Blender** (GPL; headless `blender -b -P script.py`, Metal on the Mac): a DEM mesh with imagery as its texture, a camera on a path, a sun, haze; the best control over the look and fully offline once the data is prepared, but the most assembly work and the slowest per frame; BlenderGIS can download Google satellite tiles, which we must not use. A candidate for a few hero gaps later.
   - **MapLibre Native** (headless without a browser, Node bindings): attractive, but 3D terrain in Native was still being implemented in its December 2025 newsletter ([newsletter](https://maplibre.org/news/2026-01-03-maplibre-newsletter-december-2025/)): re-check before ruling it out.
   - Not looked at in detail: deck.gl, three.js-based viewers (iTowns), PyVista or QGIS 3D; none has a ready GPX flyover with export, so they are unlikely to beat the first two.
   **Outcome (2 Oct):** MapLibre Native was prototyped first and its look and camera were approved, so CesiumJS, Blender and MapLibre GL JS stay as fall-backs only (GL JS in a browser if Native's terrain branch is not merged and breaks). The imagery licence is the same question for every engine.
3. **N3: Earth Studio, by hand, for a few hero gaps:** we write the KML (camera path along the track, keyframes at the speed we want) and the user renders it in the browser and drops the file in; non-commercial, watermarked, one gap at a time. Worth trying on two or three gaps to see how the look compares with N2.

**How a generated clip enters the edit (the same for all options):**
- A **synthetic clip** in the project: `kind: "synthetic"`, start and end UTC (the gap, or the chosen stretch), the speed-up, the style and parameters (a hash for the cache), the rendered file; no `.OSV`, no sound. The gap finder lists spans between consecutive clips that have track coverage and are longer than a threshold [20 minutes].
- The **script writer** gets them in the context pack as clips with what the track and the places say (km range, pace, altitude, daylight, place names along the way, "no footage: generated flight") so narration can sit on them; the planner gives each a block like any clip. The film's length budget fixes the speed-up (gap seconds divided by the seconds allocated).
- **Rendering needs a flat (non-360) source (built, N1c):** a window from a synthetic clip is an ordinary 2D video scaled to the film (`render/synthetic.py`), played as it is: the map clip has its own overlay baked in at its speed-up, so no piecewise time map is needed in the film render. The same source serves the 3D flyover clips. A flat source is also what imported phone or drone video would need.
- **On demand:** from the map or a chart (Milestone M) select a stretch, choose a speed or a length, and a new variant renders and caches under its key; the draft script can then use it.

**Open decisions:** (N1 and N2 are built and connected to the film; Windows flyover untried); which imagery for N2 and its licence; the gap threshold; whether the film is non-commercial (decides N3); the picture size [same as the film].
- **Done when (N1):** unit tests: the gap finder (spans, threshold, no coverage means no gap); the speed-up arithmetic; the synthetic clip's time map is monotonic and covers the gap once; a synthetic clip is accepted by the script pack and the planner. A rendered 30 s clip of one Legends night shows the right position at three known moments (checked against the overlay's position marker).

**Final render renders generated clips itself (8 Oct):** the final film (and a still, when the clip has been made) renders every generated window from its original sources at the film's own frame rate and size (`edit/synth_render.py`, kept in `synthetic/film/`), and a point camera on a clip is cut from the original footage; the clips in `synthetic/` are what the preview plays. See `progress/2026-10-music-upscale.md`.
